# 工作流状态更新器规范

## 1. 需求概述

添加一个定时任务，定期拉取执行历史中的任务，从而更新工作流执行的状态、结束时间等信息。

## 2. 功能需求

### 2.1 定时任务功能
- 定期检查数据库中的工作流执行历史记录
- 对于状态不是 "completed" 的记录，调用 Gitea API 获取最新状态
- 更新数据库中的状态、结束时间等信息
- 支持可配置的检查间隔

### 2.2 状态更新逻辑
- 检查所有状态为 "running" 或其他非 "completed" 状态的工作流执行记录
- 对于每条记录，调用 Gitea API 获取最新的运行状态
- 根据 API 返回的状态更新数据库记录
- 当工作流执行完成时，更新结束时间和结论

## 3. 技术实现

### 3.1 服务设计
- 创建 `WorkflowStatusUpdaterService` 类，负责定时更新工作流状态
- 该服务应该依赖于 `WorkflowService` 和 `GiteaExtensionsDbContext`
- 提供 `UpdateWorkflowStatusesAsync` 方法，用于执行状态更新逻辑

### 3.2 定时任务配置
- 在 `Program.cs` 中使用 `IHostedService` 或 `IHostedLifecycleService` 配置定时任务
- 默认检查间隔为 1 分钟
- 支持通过配置文件调整检查间隔

### 3.3 状态更新实现
- 从数据库中获取所有状态不是 "completed" 的 `WorkflowRunHistory` 记录
- 对于每条记录，调用 `GiteaApiClient.GetWorkflowRunAsync` 获取最新状态
- 根据返回的 `WorkflowRun` 对象更新数据库记录
- 处理 API 调用失败的情况，避免影响其他记录的更新

## 4. 数据模型

### 4.1 现有模型
- `WorkflowRunHistory`：包含工作流执行的详细信息，包括状态、时间戳等
- `WorkflowRun`：从 Gitea API 返回的工作流运行信息

### 4.2 数据更新策略
- 仅更新状态、结束时间、结论等字段
- 保持其他字段不变
- 记录最后更新时间

## 5. 错误处理

### 5.1 API 调用错误
- 当 API 调用失败时，记录错误日志
- 跳过当前记录，继续处理其他记录
- 避免因为单个记录的错误而中断整个更新过程

### 5.2 数据库更新错误
- 当数据库更新失败时，记录错误日志
- 跳过当前记录，继续处理其他记录

## 6. 性能考虑

### 6.1 批量处理
- 每次处理的记录数量应该有合理的限制
- 避免一次性处理过多记录导致系统负载过高

### 6.2 并发控制
- 确保定时任务的执行不会与其他操作产生冲突
- 考虑使用锁或其他机制避免并发更新

## 7. 测试需求

### 7.1 单元测试
- 测试 `WorkflowStatusUpdaterService` 的核心逻辑
- 测试状态更新的各种场景
- 测试错误处理机制

### 7.2 集成测试
- 测试定时任务的配置和执行
- 测试与 Gitea API 的交互
- 测试数据库更新的正确性

## 8. 实现步骤

1. 创建 `WorkflowStatusUpdaterService` 类
2. 实现 `UpdateWorkflowStatusesAsync` 方法
3. 在 `Program.cs` 中配置定时任务
4. 编写测试用例
5. 测试功能的正确性

## 9. 验收标准

- 定时任务能够按照配置的间隔执行
- 工作流执行状态能够及时更新
- 结束时间和结论能够正确记录
- 错误处理机制能够正常工作
- 性能满足要求，不会对系统造成过大负载

## 10. 风险评估

### 10.1 潜在风险
- API 调用频率过高可能导致 Gitea 服务器负载增加
- 数据库更新操作可能影响系统性能
- 定时任务执行失败可能导致状态更新不及时

### 10.2 缓解措施
- 合理设置检查间隔
- 实现批量处理和限流机制
- 添加错误处理和重试机制
- 监控定时任务的执行状态
